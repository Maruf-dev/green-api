# Подготовка к собеседованию — чат MAX на GREEN-API (React)

Этот файл — «шпаргалка» по проекту: что сделано, из каких блоков состоит, как
выполнен каждый пункт ТЗ и какие вопросы могут задать на собеседовании.

---

## 1. Что за проект

Веб-приложение (прототип) для отправки и получения **текстовых** сообщений в
мессенджере **MAX** через сервис **GREEN-API**. Интерфейс повторяет веб-версию
чата MAX (web.max.ru): слева список чатов и поиск, справа окно переписки.

- **Стек:** React 18, Vite 4, чистый CSS, `fetch`. Без отдельного backend.
- **Точка входа:** `index.html` → `src/main.jsx` → `src/App.jsx`.
- **Окружение:** Node.js 16+ (проверено на Node 16.20).

## 2. Как запустить и что показать

```bash
npm install
npm run dev        # http://localhost:5173
```

1. Ввести `idInstance` и `apiTokenInstance` из личного кабинета GREEN-API → «Войти».
2. Нажать «+» → ввести номер телефона получателя → «Создать чат».
3. Написать текст → «Отправить».
4. Получатель отвечает в MAX → ответ появляется в чате сам.

Сборка production:

```bash
npm run build      # dist/
npm run preview    # локальный просмотр сборки
```

## 3. Архитектура и поток данных

```
Браузер (React) ──HTTPS──▶ api.green-api.com (GREEN-API) ──▶ MAX
        ▲                                                       │
        └──────── ReceiveNotification (опрос очереди) ◀─────────┘
```

Ключевая идея: приложение **полностью клиентское**. GREEN-API отдаёт заголовок
`Access-Control-Allow-Origin: *`, поэтому CORS не мешает и отдельный сервер не нужен.

Поток работы:

1. **Вход** → `getStateInstance` (проверка учётных данных).
2. (опц.) **`setSettings`** с пустым `webhookUrl` и `incomingWebhook: "yes"` —
   включаем получение входящих по технологии HTTP API.
3. **Новый чат** → `checkAccount` (получаем `chatId` по номеру телефона).
4. **Отправка** → `sendMessage` (метод `SendMessage`).
5. **Приём** → цикл `receiveNotification` → обработка → `deleteNotification`.

## 4. Разбор по файлам и блокам

### `src/main.jsx` — точка входа
Монтирует `<App />` в `#root`, подключает стили (`styles.css`, `chat.css`).

### `src/App.jsx` — «мозг» приложения
Хранит состояние и связывает всё вместе:
- **состояние:** `creds` (учётные данные), `chats` (чаты + сообщения),
  `activeChatId`, `dialogOpen`, `banner` (уведомления об ошибках/успехе);
- `handleLogin` — сохраняет учётные данные в `localStorage`, вызывает `setSettings`;
- `handleLogout` — очищает всё;
- `resolveNewChat(phone)` — по номеру через `checkAccount` создаёт чат;
- `handleSend(text)` — оптимистично добавляет «пузырь» и вызывает `sendMessage`
  (при ошибке помечает сообщение как `failed`);
- `handleNotification(notification)` — разбирает входящее уведомление
  (`incomingMessageReceived` + `textMessage`), кладёт в чат, считает непрочитанные;
- вызывает хук `useNotificationPolling` и отдаёт статус в сайдбар.

### `src/api/greenApi.js` — клиент GREEN-API
Тонкая обёртка над `fetch`. Базовый адрес: `{apiUrl}/waInstance{idInstance}`.
Функции: `getStateInstance`, `setSettings`, `checkAccount`, `sendMessage`,
`receiveNotification`, `deleteNotification`. Разбирает ответ, бросает понятные
ошибки (`HTTP 401: ...`). Считается «грязной» частью — знает только про транспорт.

### `src/hooks/useNotificationPolling.js` — приём сообщений
Цикл: `receiveNotification` → обработка → `deleteNotification` → повтор.
Если очередь пуста — пауза 1.5 c, при ошибке — 3 c. Возвращает
`{ status: 'idle' | 'running' | 'error' }`. Корректно останавливается при
размонтировании (флаг `stopped`).

### `src/components/*` — представление
- **`LoginScreen.jsx`** — форма входа (`idInstance`, `apiTokenInstance`, опц. `apiUrl`),
  чекбокс «включить HTTP API», проверка через `getStateInstance`.
- **`Sidebar.jsx`** — список чатов, поиск, кнопка «+», статус подключения, «Выйти».
- **`ChatHeader.jsx`** — шапка открытого чата (имя, `chatId`).
- **`MessageList.jsx`** — лента «пузырей» с авто-прокруткой вниз.
- **`MessageInput.jsx`** — поле ввода (Enter — отправить, Shift+Enter — перенос).
- **`NewChatDialog.jsx`** — модалка создания чата по номеру телефона.
- **`Avatar.jsx`** — круглый аватар с первой буквой имени.

### `src/utils/phone.js` — работа с номером
`normalizePhone` (8XXXXXXXXXX → 7XXXXXXXXXX, добавляет код РФ), `isValidPhone`
(только РФ `7` и РБ `375`), `formatPhone` (красивый формат для отображения).

### `src/styles.css`, `src/chat.css` — оформление
Макет как в web.max.ru: сайдбар + область чата, «пузыри» входящих/исходящих,
бейдж непрочитанных, статус-индикатор подключения.

## 6. Сценарий из «Ожидаемого результата» — пошагово

1. **Пользователь переходит на сайт и вводит учётные данные** (`idInstance`,
   `apiTokenInstance`).
   → `LoginScreen` вызывает `getStateInstance`. При успехе данные сохраняются в
   `localStorage`, и рендерится основной экран `App`.

2. **Вводит номер телефона получателя и создаёт новый чат.**
   → `NewChatDialog` нормализует номер (`normalizePhone`) и вызывает `checkAccount`.
   В ответ приходит `chatId`; чат добавляется в список и открывается.

3. **Пишет текстовое сообщение и отправляет.**
   → `MessageInput` → `handleSend` → «пузырь» добавляется оптимистично →
   `sendMessage` отправляет текст; после ответа сервера локальный id заменяется на
   `idMessage`.

4. **Получатель отвечает в MAX.**
   → GREEN-API кладёт уведомление в очередь.

5. **Пользователь видит ответ в чате.**
   → Хук `useNotificationPolling` забирает уведомление
   (`typeWebhook: 'incomingMessageReceived'`, `typeMessage: 'textMessage'`),
   `handleNotification` добавляет его в ленту и увеличивает счётчик непрочитанных,
   затем уведомление подтверждается через `deleteNotification`.

## 7. Ключевые технические решения (и почему так)

- **Опрос вместо webhook.** HTTP API GREEN-API работает по схеме «очередь + опрос»:
  `ReceiveNotification` возвращает одно уведомление (FIFO) или пусто, после
  обработки его нужно подтвердить через `DeleteNotification`. Это позволяет
  обойтись без публично доступного сервера для приёма webhook.
- **Клиентское приложение без backend.** GREEN-API отдаёт `Access-Control-Allow-Origin: *`
  → браузер может обращаться напрямую. Это упрощает развёртывание (достаточно статики).
- **`setSettings` при входе.** Чтобы включить получение входящих по HTTP API,
  отправляем `{ webhookUrl: '', incomingWebhook: 'yes' }`. Опцию можно отключить
  галочкой на экране входа.
- **Оптимистичное добавление своего сообщения.** «Пузырь» показывается сразу
  (локальный id `local-...`), затем заменяется на реальный `idMessage`; при ошибке
  помечается как `failed` (красный «!»).
- **Защита от дублей.** Входящее сообщение не добавляется, если в чате уже есть
  сообщение с таким же `id`.
- **Состояние в `localStorage`.** Учётные данные сохраняются, чтобы не вводить
  их каждый раз; история сообщений — в памяти вкладки.

## 8. Возможные вопросы на собеседовании (Q&A)

**Q: Почему проект не использует backend?**
A: GREEN-API разрешает CORS (`Access-Control-Allow-Origin: *`), поэтому браузер
обращается к API напрямую. Backend нужен только для Telegram-режима (там CORS закрыт).

**Q: Что происходит между «получить уведомление» и «показать его в чате»?**
A: `receiveNotification` → `handleNotification` (фильтрация по типу → добавление в
ленту → счётчик непрочитанных) → `deleteNotification` (подтверждение).

**Q: Почему `checkAccount` поддерживает только РФ и РБ?**
A: Так устроен метод GREEN-API (MAX): он принимает 11–12 цифр с кодами `7`/`375`.
Поэтому `normalizePhone` и `isValidPhone` ограничены этими правилами.

**Q: Как отличить входящее от исходящего?**
A: Исходящие добавляем сами при отправке; входящие приходят уведомлением
`incomingMessageReceived` и помечаются `direction: 'in'`.

**Q: Как реализована авторизация?**
A: Экран входа проверяет данные через `getStateInstance`. При `HTTP 401` показываем
«Неверные idInstance или apiTokenInstance». При успехе креды кэшируются в `localStorage`.

**Q: Как считается число непрочитанных?**
A: Если чат не активен — инкремент `chat.unread`; при открытии чата счётчик
сбрасывается (`handleSelectChat`).

**Q: Что будет при перезагрузке страницы?**
A: Креды восстановятся из `localStorage`; чаты и сообщения — нет (хранятся в памяти
вкладки). Это осознанное упрощение для прототипа.

**Q: Как обеспечить безопасность токена?**
A: Для прототипа токен лежит в `localStorage`. В проде его не стоит хранить в
браузере напрямую — правильнее проксировать запросы через backend и хранить токен
на сервере. (В Telegram-режиме токен передаётся на локальный прокси в теле запроса.)

## 9. Ограничения и что можно улучшить

- Нет истории сообщений между перезагрузками (можно добавить IndexedDB / backend).
- Нет поддержки медиа/групп — только текст (по ТЗ).
- Опрос вместо webhook (для продакшена лучше webhook + backend).
- Пагинация списка чатов и виртуализация ленты при больших объёмах.

## 10. Дополнительно: режим Telegram (запасной вариант)

Ключи GREEN-API получить не удалось, поэтому добавлен второй провайдер —
**Telegram Bot API**, чтобы приложение можно было продемонстрировать вживую.

- Вход по **токену бота** (@BotFather), проверка через `getMe`.
- Создание чата по `id` или `@username` (`getChat`); номер телефона не поддерживается.
- Отправка — `sendMessage`, приём — `getUpdates` (long polling с `offset`).
- Нужен локальный **прокси** `server.mjs` (у `api.telegram.org` нет CORS).
- Запуск: `npm run dev:all`.

Оба провайдера живут за единым интерфейсом в `src/providers/index.js`
(`connect`, `resolveChat`, `send`, `parseEvent`), а на экране входа есть
переключатель. Код MAX/GREEN-API — основной и соответствует ТЗ.
